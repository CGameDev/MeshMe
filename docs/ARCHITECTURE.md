# Mesh Me360 — Architecture Specification

This architecture is fixed for v1.0 unless the repository owner explicitly changes it.

## 1. High-level design

```text
┌──────────────────────────────────────────────────────────────────────┐
│ MeshMe360.Desktop.exe — .NET 8 / WPF                               │
│                                                                      │
│  Window/session       Settings          Recent files                 │
│  File associations    Crash marker      Logging                      │
│  Updates/installer    Native dialogs    WebView2 lifecycle           │
│                                                                      │
│  ┌──────────────────────── WebView2 ──────────────────────────────┐  │
│  │ Mesh Me360 web UI                                              │  │
│  │                                                                │  │
│  │ Fusion-inspired layout                                        │  │
│  │ Three.js viewport                                             │  │
│  │ Preserved BumpMesh engine                                     │  │
│  │ Texture/mask/subdivision/displacement/decimation/export       │  │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

The WPF host is not a geometry engine. The JavaScript/Three.js layer is not an operating-system integration layer.

## 2. Projects

### `src/MeshMe360.Desktop`
WPF executable.

Responsibilities:
- main window lifecycle
- WebView2 initialization
- application data paths
- startup argument parsing
- recent files
- settings
- logging
- crash/session state
- file associations
- native save/open integration where needed
- updater
- diagnostics host information
- internal bridge endpoints

### `src/MeshMe360.Core`
Small .NET class library containing:
- settings models
- recent-file models
- update models
- host bridge message DTOs
- recovery metadata models
- path helpers
- version/schema constants

Do not move web geometry into this project.

### `src/MeshMe360.EngineWeb`
Packaged web application.

Subfolders:

```text
upstream/   # exact imported/preserved BumpMesh baseline and traceable modifications
app/        # Mesh Me360 UI adapter/layout/desktop bridge JS
vendor/     # local pinned browser runtime dependencies
assets/     # Mesh Me360-owned UI assets/icons if not in app/
```

The build must publish this content with the desktop app.

### `src/MeshMe360.Updater`
Create only if the chosen updater integration is cleaner outside the Desktop project. Do not create a second application unless required by the updater framework.

## 3. WebView2 application origin

Do not run Python, Node, Kestrel, HttpListener, IIS Express, or another local web server.

Map the packaged web root using WebView2 virtual-host folder mapping:

- app origin: `https://app.meshme360.local/`
- entry page: `https://app.meshme360.local/index.html`

Use `CoreWebView2HostResourceAccessKind.DenyCors` or the narrowest resource access mode that still permits required local ES module imports. If implementation needs a different access kind for workers/modules, document the reason and retain a restrictive CSP.

## 4. Internal binary bridge origin

Use a separate internal origin:

- `https://bridge.meshme360.local/`

This is **not** a DNS/network endpoint and must never be served by a listener. Handle it using WebView2 `WebResourceRequested` interception.

### Security rules
- never expose arbitrary filesystem paths to JavaScript as fetchable URLs
- host generates opaque random tokens
- each token maps to one explicitly approved file/operation
- tokens expire when consumed or when the document/session closes
- reject unknown methods, paths, tokens, or content types
- do not allow directory enumeration
- do not allow `..` path traversal
- internal bridge responses set `Cache-Control: no-store`

## 5. Binary bridge endpoints

Exact logical endpoints for v1.0:

### `GET /file/{token}`
Purpose: host-to-web opening of a model/project selected through Explorer activation, Recent Files, or other native flow.

Host response:
- raw bytes
- correct safe content type when known; otherwise `application/octet-stream`
- headers carrying sanitized filename and extension metadata, or equivalent metadata supplied through the control-message channel

The web layer converts received bytes into a `File`/`Blob` and sends it through the same loader path used by normal browser file input. Do not create a second parser path.

### `POST /recovery/{token}`
Purpose: web-to-host autosave/recovery snapshot write.

Request body:
- serialized project/recovery binary generated by the same project serialization path used by `.bumpmesh` where feasible

Host validates:
- active recovery request token
- maximum accepted size based on available disk/known document size, not an arbitrary tiny limit
- destination remains under `%LOCALAPPDATA%\MeshMe360\Recovery\`

Write atomically:
1. write `*.tmp`
2. flush/close
3. replace/move to final snapshot name
4. update recovery metadata

### `POST /diagnostic/engine-log`
Optional internal endpoint only if large structured engine diagnostics cannot reasonably use normal web messages. Ordinary log lines should use control messages.

Do not add more bridge endpoints without documenting them here or in an implementation decision log.

## 6. Control-message bridge

Use `window.chrome.webview.postMessage(...)` and `CoreWebView2.WebMessageReceived` for small control/metadata messages.

Envelope:

```json
{
  "type": "settings.get",
  "requestId": "uuid",
  "payload": {}
}
```

Response:

```json
{
  "type": "settings.get.result",
  "requestId": "same-uuid",
  "success": true,
  "payload": {},
  "error": null
}
```

### Required message types

Host/web lifecycle:
- `web.ready`
- `host.ready`
- `host.startupFile`

Settings/theme:
- `settings.get`
- `settings.set`
- `theme.osChanged`

Recent files:
- `recent.add`
- `recent.list`
- `recent.remove`
- `recent.clear`
- `recent.open`

Document state:
- `document.stateChanged`
- `document.titleChanged`
- `document.dirtyChanged`

Recovery:
- `recovery.snapshot.begin`
- `recovery.snapshot.complete`
- `recovery.snapshot.failed`
- `recovery.list`
- `recovery.restore`
- `recovery.delete`

Updates:
- `update.status`
- `update.check`
- `update.install`

Diagnostics/logging:
- `engine.log`
- `engine.error`
- `diagnostics.webInfo`

Use request/response correlation for commands that return data. Fire-and-forget notifications may omit a response but should still contain a request/event id where useful for logs.

## 7. Opening files

### User chooses a file inside the web UI
The existing `<input type=file>` / drag-and-drop loader path may be retained because WebView2 invokes native Windows browser dialogs and supplies a real `File` object to the web engine.

### Explorer, command-line, or Recent Files
1. WPF receives/owns the filesystem path.
2. WPF validates extension/existence.
3. Host creates an opaque bridge token mapped to that exact file.
4. Host sends a `host.startupFile` or recent-open message containing token + sanitized metadata, not the raw path unless the UI specifically needs to display it.
5. Web fetches `https://bridge.meshme360.local/file/{token}`.
6. Web wraps bytes as `File` and calls the standard loader.

This avoids base64 and avoids a second geometry parser.

## 8. Saving and exporting

The web engine remains responsible for producing `.bumpmesh`, STL, and 3MF output bytes.

Use the existing browser Blob/download path or a small Mesh Me360 adapter around it.

The WPF host handles `CoreWebView2.DownloadStarting`:
- recognize operation metadata/token from the web layer
- display native Windows Save File dialog for interactive saves/exports
- set the resulting destination path on the download operation
- cancel safely if the user cancels
- update recent project path only after successful project save

Internal autosave must use `/recovery/{token}` and must not open a dialog.

## 9. Offline dependencies

Runtime browser dependencies must be local under `src/MeshMe360.EngineWeb/vendor/` or packaged equivalent.

At minimum preserve/pin what the upstream baseline uses:
- Three.js and required addons/loaders/line modules
- fflate
- meshStep and its worker/runtime dependencies for STEP/STP

Remove CDN `importmap` URLs and preconnect/preload URLs from the release web app.

`THIRD_PARTY_NOTICES.md` must record package/version/source/license.

## 10. Content Security Policy

Release app should have a restrictive CSP similar in intent to:

```text
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' blob: data:;
worker-src 'self' blob:;
connect-src 'self' https://bridge.meshme360.local;
font-src 'self';
object-src 'none';
frame-src 'none';
base-uri 'none';
```

If upstream implementation requires a narrowly different directive, document and test it. Do not use `*` merely to make errors disappear.

## 11. Application data locations

Use environment APIs, not hard-coded usernames.

```text
%APPDATA%\MeshMe360\
  settings.json
  recent.json
  Textures\

%LOCALAPPDATA%\MeshMe360\
  Logs\
  Recovery\
  Session\
  Cache\
  WebView2\UserData\
```

User projects/models remain wherever the user chooses.

## 12. Recovery architecture

### Native host
- owns active-session marker
- owns recovery directory and metadata
- writes POSTed recovery blob atomically
- prunes according to policy
- determines whether previous session was unclean

### Web layer
- knows when document is dirty/processable
- serializes project state
- requests recovery token
- POSTs binary recovery snapshot
- can restore a recovery blob through normal project load path

Do not use localStorage for large model/project recovery payloads.

## 13. Updater architecture

Use **Velopack** for v1.0 packaging/update behavior unless a documented blocker is proven during implementation.

Requirements:
- Windows x64 release packages
- GitHub Releases feed for stable updates
- dev/test channel separate from stable
- no startup blocking
- user-triggered install
- preserve AppData/LocalAppData user data

See `docs/RELEASE_AND_INSTALLER.md`.

## 14. WebView2 runtime strategy

Release artifacts must be capable of running offline on a clean supported Windows machine.

Preferred v1.0 strategy:
- package a pinned **WebView2 Fixed Version Runtime x64** with the app/release payload
- create the WebView2 environment pointing at the packaged fixed runtime
- do not require an online bootstrapper at first launch
- do not commit the large runtime binary tree to normal Git history; the release/build pipeline obtains and packages the pinned runtime

If release size becomes unacceptable, do not silently switch to online installation. Document the proposed change for owner approval.

## 15. Threading

- WPF UI thread: window and WebView2 UI lifecycle only
- geometry: remains in browser/worker/async paths from upstream
- file hashing/copy/logging/update operations: async/background .NET tasks where appropriate
- never block WPF UI while reading a large model
- never perform geometry calculations in C# merely to avoid async JavaScript work

## 16. Error boundaries

### Host errors
Show a Mesh Me360 error dialog/panel with:
- concise user message
- Copy Details
- Open Log Folder when useful

### Engine errors
Capture JavaScript errors/unhandled rejections and report to host logs with:
- timestamp
- engine version/build
- message
- stack where available
- current operation

Never log raw model bytes.

## 17. Versioning

Use semantic versioning for Mesh Me360.

- product version example: `1.0.0`
- upstream engine baseline remains separately recorded
- do not pretend Mesh Me360 version equals BumpMesh version

About/diagnostics should show both where useful:

```text
Mesh Me360 1.0.0
BumpMesh engine baseline: v1.2.0 / a6ac179
```
